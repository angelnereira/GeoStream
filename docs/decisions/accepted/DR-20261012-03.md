# Solicitud de decisión DR-20261012-03

> Se crea cuando se cumple una condición de parada de `20_AGENT_PROTOCOL.md` §6. Se guarda como issue o en `docs/decisions/pending/`.

- **Abierta por:** agente de código
- **Fecha:** 2026-10-12
- **Tarea afectada:** T-F2-03 (`geostream admin`)
- **Condición de parada:** (1) contradicción entre `docs/16_OPERATIONS.md` §3 y `docs/05_DOMAIN_MODEL.md` §3 (INV-TEN-1)

## Qué se encontró

`docs/16_OPERATIONS.md` §3 documenta el CLI de administración con estas firmas exactas:

```text
geostream admin app create     --tenant <ten_…> --name <nombre> [--device-scopes s1,s2] [--origins o1,o2]
geostream admin app list       --tenant <ten_…>
geostream admin app disable    --app <app_…>
geostream admin key create     --app <app_…> [--scopes s1,s2] [--label txt] [--expires-in 90d]
geostream admin key list       --app <app_…>
geostream admin key revoke     --key <key_…>
geostream admin tenant disable --tenant <ten_…>
```

`docs/05_DOMAIN_MODEL.md` §3, INV-TEN-1 dice:

> INV-TEN-1: ningún recurso referencia recursos de otro tenant. Toda consulta filtra por `tenant_id` derivado del principal.

Las cuatro últimas comandos referencian una entidad (`app_…`, `key_…`) **sin** `--tenant`, pero toda consulta de repositorio de `gs-store` filtra por `tenant_id`. El CLI de operador no tiene un principal de tenant (su actor es el operador, `actor_kind=OPERATOR` según `10` §8.3), así que el `tenant_id` de esas comandos solo puede derivarse de la propia entidad.

## Por qué bloquea

Sin decidir, no se puede implementar `app disable`, `key create`, `key list` ni `key revoke`: o bien se desvía la firma documentada (haciendo `--tenant` obligatorio), o bien se resuelve el tenant desde la entidad (añadiendo a `gs-store` dos consultas sin filtro de tenant, `ApplicationRepository::find_by_id` y `ApiKeyRepository::find_by_id`).

## Opciones

1. **Operador resuelve el tenant desde la entidad** (implementada en T-F2-03): la CLI conserva las firmas de `16` §3; `gs-store` expone `find_by_id` para resolución de operador y toda **mutación** sigue filtrando por el `tenant_id` resuelto. Impacto: dos métodos de lectura nuevos en `gs-store`, comentados como resolutor de operador; invariante intacta en todas las escrituras.
2. **`--tenant` obligatorio en las cuatro comandos**: se cambia `docs/16` §3. Impacto: cambio documental (el bloque de firmas es normativo), la UX del runbook y los ejemplos de `15` quedarían desalineados hasta corregirlos.
3. **Añadir un principal de operador con tenant efectivo**: impacto grande (nuevo modelo de identidad, ADR propio); desproporcionado para F2.

## Recomendación del solicitante

Opción 1. Es la única que cumple las firmas documentadas sin tocar ningún documento normativo, y las escrituras siguen filtrando por `tenant_id`. La lectura sin filtro es acotada, explícita y necesaria para cualquier consola de operador (la API de administración de F15 la necesitará igual).

## Decisión (la completa el propietario)

- Opción elegida: Opción 1 (el operador resuelve el `tenant_id` desde la entidad mediante `find_by_id` y toda mutación posterior filtra por el `tenant_id` resuelto).
- Documentos/ADR a actualizar: `docs/05_DOMAIN_MODEL.md` §3, `docs/16_OPERATIONS.md` §3, `docs/PROGRESS.md`.
- Fecha: 2026-10-15
