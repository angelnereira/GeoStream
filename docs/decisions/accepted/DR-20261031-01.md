# Solicitud de decisión DR-20261031-01

- **Abierta por:** agente de código, por encargo del propietario
- **Fecha:** 2026-10-31
- **Tarea afectada:** FR-AUTH-009 (F15), FR-ADM-004 (F15); integración con los demás proyectos del propietario
- **Condición de parada:** (3) cambio de contrato y de seguridad

## Qué se encontró

El propietario pide que los usuarios puedan «registrar cuentas o un perfil» y «autenticarse de manera más rápida»,
de forma compatible con sus otros proyectos, para que GeoStream sea un servicio reutilizable.

- `docs/06_IDENTITY_AUTH.md` §2: GeoStream no tiene usuarios finales; confía en el backend del integrador, que emite
  tokens de dispositivo con `POST /v1/tokens` y una API key.
- `docs/03_REQUIREMENTS.md` FR-AUTH-009 (COULD, F15): «el integrador firma tokens con una clave pública registrada
  (JWKS)». Aceptación: «definida en un ADR antes de implementarse».
- FR-ADM-004 (COULD, F15): API HTTP de administración; «requiere ADR y modelo de amenazas propio».
- El servicio `identity` de Plenty-Pay (Railway, proyecto `gravital-production`) firma con un secreto simétrico
  (variables `ACCESS_TOKEN_SECRET`, `REFRESH_TOKEN_SECRET`) y autentica con OTP y WebAuthn. Un token firmado con un
  secreto simétrico solo puede verificarlo quien tiene el secreto, que también puede **acuñarlo**.

## Por qué bloquea

Cualquier alternativa a «el backend de cada proyecto pide el token» cambia la autenticación (nuevo emisor de
confianza, nuevas rutas, nuevas tablas) y adelanta trabajo de F15. `AGENTS.md` prohíbe hacerlo sin decisión.

## Opciones

1. **Intercambio de token por el backend de cada proyecto (ya implementado).** Cada proyecto es una aplicación con su
   API key; su backend verifica la sesión del usuario con su propia identidad y llama a `POST /v1/tokens`. Cero
   cambios en GeoStream; documentado en `15` §10.3. Coste: cada proyecto expone un endpoint de tokens (unas 30 líneas).
2. **Federación por JWKS (FR-AUTH-009).** GeoStream acepta tokens firmados por la identidad del proyecto (EdDSA o
   ES256) y publicados en un JWKS registrado por aplicación; mapea `sub` a `external_subject_id`. Requiere: ADR, tabla
   de emisores por aplicación, caché de JWKS con rotación, validación de `iss`/`aud`/`exp`, scopes máximos por emisor y
   pruebas negativas de `06` §4.3. **Requiere además que `identity` de Plenty-Pay firme con clave asimétrica** (hoy usa
   secreto simétrico, inaceptable para federar).
3. **Consola de registro de proyectos (FR-ADM-004).** Endpoints HTTP para que un desarrollador cree tenant, app y API
   key por autoservicio. Requiere ADR, modelo de amenazas (abuso de altas, enumeración, rotación de keys) y cuotas.
4. **Cuentas de usuario final dentro de GeoStream.** Contradice `06` §2 y el principio de que GeoStream no guarda
   datos personales del usuario; no recomendado.

## Recomendación del solicitante

Opción 1 ahora (funciona hoy y no debilita nada). Abrir ADR para la opción 2 cuando `identity` publique un JWKS
asimétrico; es la que da el «inicio de sesión rápido» sin endpoint propio en cada proyecto. Opción 3 solo si
GeoStream se ofrecerá a terceros fuera de los proyectos del propietario.

## Decisión (la completa el propietario)
- Opción elegida: Opción 1 ahora (intercambio de token por el backend de cada proyecto, ya implementado); la opción 2 (JWKS, FR-AUTH-009) queda aprobada como siguiente paso, condicionada a que `identity` de Plenty-Pay firme con clave asimétrica y a su ADR. Aprobada por el propietario en conversación («Dale procede con todo», 2026-10-31).
