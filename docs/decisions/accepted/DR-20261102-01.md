# Solicitud de decisión DR-20261102-01

- **Abierta por:** agente (a partir de la petición de seguimiento de entregas para Plenty-Pay)
- **Fecha:** 2026-11-02
- **Tarea afectada:** T-F8-05 (Flutter Web) y T-F15-12 (mapa en vivo); sin ID propio para el enlace de seguimiento
- **Condición de parada:** (3) cambio de contrato o de seguridad

## Qué se encontró
Plenty-Pay quiere que el cliente de una entrega vea al repartidor moverse en un mapa en tiempo real, como Uber o inDrive.

- `contracts/openapi/geostream.v1.yaml`, `getSnapshot`: `x-gs-auth: { application: 'locations:read', device: none }`. **Un dispositivo (el navegador del cliente) no puede leer el snapshot REST**; solo una aplicación con su API key.
- `docs/15` §3.2 ya describe el patrón: el backend crea un sujeto invitado `guest:<id aleatorio>`, lo añade a la sesión con `{read}` y le emite un token `platform=WEB` con `stream:connect`. El enlace público debe llevar a **una página del integrador** que obtenga el token: nunca el `session_id` como único secreto.
- `docs/17`: `GS_STREAM_JSON_ENABLED` vale `false` en `prod` (`gs.v1.json` apagado). En producción el stream habla solo Protobuf binario (`gs.v1.proto`).
- Un cliente web hoy tendría que decodificar Protobuf en el navegador; el portal no tiene Dart generado desde `contracts/proto` (es T-F8-05).

## Por qué bloquea
Hay cuatro formas de entregar el seguimiento al cliente final y dos de ellas cambian la superficie de seguridad de producción. Elegir una es una decisión del propietario.

## Opciones
1. **El backend del integrador hace de relevo del snapshot.** La página de seguimiento de Plenty-Pay consulta a su propio backend cada 2–5 s y este lee `GET /v1/sessions/{id}/snapshot` con su API key (`locations:read`). Sin cambios en GeoStream; funciona hoy. Latencia de segundos, no de milisegundos; la API key nunca sale del backend.
2. **Navegador con WebSocket y Protobuf.** El backend emite un token de invitado (`stream:connect`) y la página abre `wss://…/v1/stream` con `gs.v1.proto`. Es la vía de tiempo real y la que ya describe `15` §3.2. Requiere el cliente Flutter Web/Dart generado desde el contrato (T-F8-05) y que GeoStream publique un widget de mapa reutilizable. Sin cambios en el servidor.
3. **Encender `gs.v1.json` en producción.** Simplifica el cliente web (JSON en vez de Protobuf), pero revierte una decisión de endurecimiento de `prod` (mayor superficie de parseo expuesta a Internet). Necesita revisión de amenazas.
4. **Enlace de seguimiento alojado por GeoStream** (un endpoint que emite un token de solo lectura de vida corta para una sesión). Es la experiencia más cómoda, pero es un cambio de contrato y de modelo de amenazas (un token en una URL pública que revela ubicación en vivo): exige ADR propio, caducidad, revocación y límites de tasa.

## Recomendación del solicitante
**Opción 1 ya** para que Plenty-Pay tenga seguimiento utilizable esta semana sin tocar la seguridad, y **opción 2** como destino de tiempo real (T-F8-05). No recomiendo 3 ni 4 sin un análisis de amenazas previo.

## Decisión (la completa el propietario)
- Opción elegida: **1**, el backend del integrador hace de relevo del snapshot. La opción 2 (WebSocket con Protobuf,
  T-F8-05) queda como destino de tiempo real; las opciones 3 y 4 no se hacen sin un análisis de amenazas previo.
- Documentos/ADR a actualizar: `15` §3.2 y §6.3, `examples/tracking-relay-node`, `TECH_DEBT.md`.
- Fecha: 2026-11-02
